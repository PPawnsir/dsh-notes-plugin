# Agent 工作记忆 v0 机制设计（沉淀 / 模板 / 治理接入）

> 状态：**待评审** · 版本：v0 设计稿（r2，并入两条主窗口裁决） · 日期：2026-10-04
> 上游决策：方向「可治理的 Agent 工作记忆层」（笔记 `n-muqyk2ve1sqx`）；第一步「Agent 主动写」——自动沉淀。
> 本文档只产出机制设计，不含代码实现；评审通过后按第 10 章分期立项。
>
> **已并入的主窗口裁决**：

> - 裁决 B（规模与召回）：日志默认隐身、聚合压条数（对数增长）、检索分层、存储量化背书（§6、§7）。

## 1. 背景与目标

Agent 会话结论是「一次性」的：今天做了什么、改了哪些文件、遗留什么问题，会话一关就丢。笔记插件已解决「约定与资料的沉淀与注入」，但**工作过程本身的沉淀**仍靠用户手动速记，覆盖率极低。

工作记忆 v0 的目标：**让每个会话的工作结论以「工作日志」形态低成本沉淀进本地笔记库，并接受现有治理体系管理**，为后续语义检索与跨会话接力打底。同时守住一条底线：**日常笔记体验永不因沉淀改变**——日志默认隐身、条数增长对数化、检索压力可控（裁决 B，§6/§7 量化）。

### v0 做 / 不做

| 做 | 不做 |
| --- | --- |
| 工作日志（kind=log）模板与写入通道 | 通用记忆引擎 / 向量检索 |
| 约定引导的 agent 自主沉淀（主路径） | 强制自动沉淀（idle 默认不写） |
| host 自动总结（可选开关，默认关） | 读取冷会话转录（~10s/个，0.1.7 教训） |
| 日志默认隐身（inject 硬 false / recall 默认 false / 列表与默认搜索排除） | 日志混入日常浏览、目录注入、默认搜索 |
| 日志卫生：超窗旧日志按月聚合提名（只提名不执行） | 自动删除 / 自动合并日志 |
| front-matter 检索字段预留 | entities/topics 的自动抽取（v2+） |

## 2. 核心机制总览

```
┌─ 引导层 ────────────────────────────────────────────────┐
│ 预填约定笔记（inject=true, 用户可见/可改/可停）            │
│  → 单一注入源：复用 order 130 约定注入，无独立管线          │
├─ 写入层 ────────────────────────────────────────────────┤
│ 主：agent 自主写 note_manage create/update (kind=log)     │
│ 副：host 自动总结（settings.memoryAutoSummary=true 才启用）│
├─ 存储层 ────────────────────────────────────────────────┤
│ 普通笔记文件（n-*.md front-matter + 正文），同库同格式      │
├─ 治理层 ────────────────────────────────────────────────┤
│ 默认隐身（inject 硬 false / recall 默认 false /            │
│   列表与默认搜索排除 kind=log，筛选中心为专入口）           │
│ 日志卫生（超 7 天周聚合、超 90 天月聚合，只提名不执行）     │
│ 敏感识别继承 · 回收站/导入导出全链路复用                   │
├─ 检索层 ────────────────────────────────────────────────┤
│ L1 关键词内存扫描（万条无压力）· L2 结构化过滤（v0）       │
│ L3 语义引擎插拔位（质量升级，非必需）                      │
└─────────────────────────────────────────────────────────┘
```

设计第一原则：**日志就是普通笔记**。不新增存储、不新增注入通道、不新增删除通道——全部复用现有机制，新增面收敛在「一个 kind + 一个模板 + 一个启用流程 + 默认隐身口径 + 一类治理提名」。

## 3. ① 沉淀触发时机

候选三档对比：

| 触发 | 通道现状 | 可靠性 | 成本 | 结论 |
| --- | --- | --- | --- | --- |
| **约定引导 agent 自主判断**（任务完成 / 会话收尾 / 用户示意） | 约定注入（order 130）已有 | 高——agent 有完整上下文，能判断「一个阶段结束了」 | 零增量成本 | **主路径** |
| **用户显式命令**（"记一下今天的工作"） | 零通道依赖 | 最高 | 零 | **主路径之一**（引导模板内置响应指令） |
| **host 监听 idle 自动总结** | `ctx.on('agent/status')` 已有（派发闭环在用） | **低**——idle≠语义完成（派发闭环调研结论：idle 可能是报错/追问/部分处理后的停顿） | LLM 调用成本 + 延迟 | **可选开关，默认关**（见 §5.3） |
| 定时摘要 | 无合适 cron 通道，定时≠收尾 | 低 | 高 | 不做 |

结论：**默认「约定引导 + 显式命令」双触发；idle 仅作为可选 host 自动总结的触发信号，且必须配去抖与去重（§5.3）**。v0 不把 idle 当完成信号做任何自动状态变更（沿用派发闭环的教训）。

## 4. ② 沉淀内容与模板

### 4.1 新增 kind=log（而非复用 note+tag）

**决策：新增 `kind='log'`。** 论证：

1. **模板挂载点**：KIND_TEMPLATES 按 kind 预填骨架（host/client/app.html/原型四处同源，check.js 断言一致），日志有固定结构，需要独立模板；
2. **治理语义不同**：日志的生命周期是「当日追加合并 → 周/月聚合 → 长期留存备查」，与 note 的「过期未引用即提名清理」相反——日志**永不被过期/孤儿清理提名**（它是记录而非参考资料），且需要**默认隐身**（裁决 B①）——两者都要求 kind 级区分；
3. **检索与筛选**：筛选中心类型组、note_search/note_manage 的 kind 枚举按 kind 过滤，日志的专入口（筛选中心 kind=log）依赖独立 kind；
4. **成本可控**：新增 kind 的改动面是已知且机械的（§9 清单），check.js 有现成的同源断言模式兜底。

### 4.2 日志模板（KIND_TEMPLATES.log）

```markdown
## 做了什么

（本会话完成的任务/阶段，一句话一条）

## 改动

（改动的文件/配置/数据，路径 + 一句话）

## 遗留与后续

（未完成事项、已知风险、下次接续的入口）

## 相关笔记

（[[n-xxxxxxxx]] 双链引用本库相关笔记；无则空）
```

同日多次追加时，在正文尾部追加 `## HH:mm 续` 小节（复用速记合并的时间戳小节模式）。

### 4.3 归键与合并策略

**决策：一会话一天一条（sessionId + logDate 归键），同日追加合并。** 对比：

| 策略 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 一会话一条 | 最省 | 跨天后单条无限膨胀，聚合粒度丢失 | 否 |
| 同主题同天一条 | 语义内聚 | 依赖主题分类（异步、会漂移），合并判定复杂易错 | 否 |
| **一会话一天一条** | 归键确定（sessionId+logDate），agent 易执行（先 list kind=log 查当天日志，有则 update 追加，无则 create） | 同天多会话产生多条 | **采用**；条数压力由日志卫生两级聚合收拢（§6.3） |

- 标题：`工作日志 · <工作区名> · <YYYY-MM-DD>`（沿用 buildQuickTitle 的三段式风格）；
- `folder`：启用沉淀时自动创建/复用虚拟文件夹「工作日志」，日志默认落入；
- front-matter：`sessionId`/`cwd` 沿用现有自动填充；新增 `logDate`（见 §7.2）。

## 5. ③ 写入通道（裁决 A 为核心方案）

> **主窗口裁决 A（本设计的约束前提）**：沉淀引导**不做独立注入管线**，复用约定体系——启用沉淀 = 创建一条预填约定笔记（inject=true + 用户选的作用域），用户可在面板查看/编辑/停用，**单一注入源**；引导模板文案与既有反馈类约定**互相声明分工边界**防双记；启用时做**语义重叠检查**并提示确认。
>
> 理由（裁决实例）：已有「看板反馈/笔记反馈」约定引导 agent 记录使用问题；若沉淀引导走独立通道再说「写工作日志」，两套指令并存会导致双记或指令打架——注入上下文无优先级，冲突随机裁决。约定笔记方案把引导文案变成**一条普通笔记**：可见、可改、可删、可停用，与反馈约定同桶共存、边界由文案显式划分。本设计**不保留任何"独立注入管线"设想**。

### 5.1 主通道：约定引导（启用 = 创建预填约定笔记）

**启用流程**（设置卡片新增「工作记忆」区，一个入口按钮）：

```
用户点「启用沉淀引导」
  → notes-memory-guide {op:'check'}  （dry-run 零写入）
  → host 全库扫描 inject=true 的约定笔记，命中关键词
    （记录|日志|总结|沉淀|复盘|feedback|反馈）者列为「语义重叠候选」
  → 有重叠 → 确认对话框列出这些约定（标题 + 摘要），用户确认后继续
  → notes-memory-guide {op:'enable', scope, confirmed:true}
  → 创建预填约定笔记：
      title:  约定：工作日志沉淀（工作记忆 v0）
      kind:   note            （引导是行为约定，不是日志本身）
      inject: true, injectRole: 'convention'
      injectTo: 用户选择的作用域（缺省 [] = 所有会话）
      tags:   ['memory-guide']   （发现键：状态行/停用以 tag 定位，零 schema 变更）
      body:   引导模板（§5.2）
  → 同时确保虚拟文件夹「工作日志」存在
```

**停用 / 修改 / 查看**：全部是既有操作——面板里把该笔记 inject 关掉即停用、编辑正文即改引导、删除即彻底退出。**启用状态不落 settings.json**：状态 = 「存在 tag=memory-guide 且 inject=true 的笔记」，单一事实源，杜绝「设置说开了但约定被删了」的双源漂移。

**可选增强**（enable 响应中提供，前端一键执行）：对重叠检查命中的反馈类约定，提供「在其正文尾部追加一行分工声明」（复用 notes-update 追加），实现模板间**互相**声明边界。默认不勾，避免静默改用户笔记。

### 5.2 引导模板全文（预填约定笔记 body）

```markdown
【工作约定】会话工作沉淀（工作记忆 v0）

在以下时机把本会话的工作结论沉淀为工作日志（note_manage，kind=log）：
- 一个任务或阶段完成时（尤其看板任务验收/上线后）；
- 用户显式说「记一下 / 沉淀一下 / 写工作日志」时；
- 会话明显收尾（用户道别、长时间无新指令前的最后回合）。

写法：
1. 先 note_manage list（kind=log）查本会话今天是否已有日志：
   有 → update 追加一节「## HH:mm 续」；无 → create（模板骨架见 KIND_TEMPLATES.log）。
2. folder 传「工作日志」。日志默认隐身：不进系统提示、不进目录索引、
   不出现在默认列表与默认搜索——无需也不能开 inject；recall 保持默认。
3. 返回 sensitiveSuggested=true 时必须补 sensitive: true。
4. 「相关笔记」一节用 [[n-xxxxxxxx]] 双链引用本库笔记。
5. 查历史工作日志：note_search 传 kind=log（默认搜索不含日志）。

【分工边界】本约定只管「会话工作结论沉淀」（做了什么/改了什么/遗留什么）。
产品使用问题与体验反馈**不写入工作日志**——若同时注入了「看板反馈」
「笔记反馈」类约定，那些内容按那些约定记到对应文件夹。两者正交、
互不替代、互不合并。
```

边界声明是模板的**必需段落**（裁决 A②）：凡注入本约定的会话，反馈类内容仍走反馈约定，日志只收工作结论，从文案上杜绝双记。模板同时把「日志隐身 + kind=log 检索」写进约定，agent 不会因日志不出现在目录/默认搜索而误判"没写进去"。

### 5.3 副通道：host 自动总结（可选开关，默认关）

定位：约定引导的**兜底**——agent 没写（模型不听话/会话异常终止）时，由 host 补一份摘要。默认关闭，设置卡片「工作记忆」区显式开启（settings.json 顶层键 `memoryAutoSummary`，null 恢复默认关；沿用 settings-set 校验模式）。

- **触发**：复用 `ctx.on('agent/status')` idle 订阅（派发闭环同款通道），仅处理**顶层 live 会话**（`agents.roots()` 口径，排除子 agent）；
- **去抖**：idle 后延迟 5 分钟确认无新消息再动手（timer 或轻量调度；期间新 idle/running 事件重置计时）；
- **去重**：日志 front-matter 记录 `summarizedAt`；同会话同 logDate 已有日志且 `summarizedAt` 晚于最近用户消息时间 → 跳过；已有 agent 手写日志 → 改为追加「## HH:mm 自动补记」小节，不覆盖；
- **读取**：只读 **live 会话**的内存消息（开发期核验 `agents.get()` 暴露的消息面；取最近 N 回合 + 字符上限，防 token 爆量，口径参考 AI_ORGANIZE_MAX_CHARS=12000）。**冷会话不读**（sessionPersistence 冷读 ~10s/个，0.1.7 派发列表教训）；
- **生成**：走 classifyTopic 同款 `llm.stream` 通道（resolveLlmSelection：settings.llm 优先 → 跟随会话），system 提示内嵌 LOG_TEMPLATE 要求直出模板结构；
- **隐身与敏感**：产出与手写日志同口径（kind=log，inject 硬 false，recall 默认 false）；先过 `suggestSensitive()`，命中直接落 `sensitive=true`（速记同款「即发即忘」口径——自动产物没有人工回标环节）；
- **失败处理**：LLM 异常/超时 → 静默跳过 + console.error + 性能遥测计数，**绝不阻塞 idle 事件链**（派发回执同链）；连续失败不做重试风暴（每会话每天至多尝试一次，front-matter `summarizedAt` 即节流阀）。

### 5.4 两通道关系

- 写入都收敛到同一 `_create`/`_update` 内部函数与同一归键（sessionId+logDate）——**存储单路径**，隐身/治理/检索无差别；
- host 补记只在「agent 该写没写」时产生价值，因此默认关；开启后也严格遵守「已有手写日志只追加不覆盖」；
- 约定引导的注入优先级问题不存在——引导本身就是一条约定笔记，与反馈约定同桶并列，边界由文案划分（裁决 A①④）。

## 6. ④ 治理接入（含裁决 B①②：默认隐身 + 聚合压条数）

### 6.1 默认隐身（裁决 B①，机制化）

日志**默认隐身**，日常笔记体验永不因沉淀改变。四条口径全部为 host 侧强制默认值，不是 UI 隐藏：

| 面 | 机制 | 说明 |
| --- | --- | --- |
| 注入通道（order 130） | **inject 硬 false**：`_create`/`_update` 对 kind=log 强制 `inject=false`（显式传 true 也纠正，并在响应中告知） | 日志永不进系统提示 |
| 目录索引（order 131） | **recall 默认 false**：kind=log 缺省 `recall=false`（显式 true 允许——用户/agent 显式选择进目录，不算混入） | 目录不被日志刷屏；目录尾部追加一行固定提示「另有 N 条工作日志，用 note_search kind=log 检索」（有日志时恒出现，一条占位不刷屏） |
| 日常浏览列表 | `_list` 默认排除 kind=log；显式 kind=log 过滤或 `includeLogs:true` 才返回 | 面板/全窗口页默认视图零变化；**筛选中心 kind=日志 即专入口**（裁决 B① 指定的专入口形态，不新增独立视图） |
| 默认搜索 | `_search` 同款默认排除；`note_search`/`note_manage list` 传 kind=log（或 includeLogs）即召回 | 「检索时出现」= 显式 kind=log 检索，语义明确 |

例外（隐身不适用面）：回收站（includeDeleted 路径）、整理建议器、归档、导入导出、备份——**治理与数据完整性路径显式包含日志**，隐身只作用于「日常浏览与默认搜索」面。

### 6.2 敏感与遥测继承

- 敏感识别三入口全覆盖：agent create 回传 `sensitiveSuggested`（现有）、host 自动总结自动落 `sensitive=true`（速记口径）、面板手动 🔒 toggle（现有）；目录提示行不含标题正文，天然无泄露面；
- 使用遥测（useCount）、双链/反向链接索引自动覆盖日志正文。

### 6.3 日志卫生：两级聚合提名（裁决 B②，对数增长）

`notes-suggest` 新增第四类候选 `logHygieneCandidates`（dry-run 零写入，与现有三类同哲学：**只提名不执行**；执行复用归档白名单通道，成员软删除可恢复、可撤销）：

| 级 | 触发（设置键，null 恢复缺省） | 归组 | 产物 |
| --- | --- | --- | --- |
| **周聚合** | logDate 超过 `logWeekAfterDays`（缺省 **7** 天） | 按 工作区 × ISO 周 分组，同组 ≥2 条成候选 | `工作周志 · <工作区> · <YYYY-Www>`（kind=log，logDate=周首日） |
| **月聚合** | logDate 超过 `logRetentionDays`（缺省 **90** 天，0=关闭本级） | 按 工作区 × 月 分组（原始日志与周志混合归组） | `工作月志 · <工作区> · <YYYY-MM>`（kind=log，logDate=月首日） |

**合并方式决策：机械拼接（不引入 LLM 合并）。** 论证：

1. 目标是**压条数**不是压信息量——机械拼接把 N 条合成 1 条，条数目标达成且信息零丢失；LLM 摘要会丢细节，而日志的价值恰在细节可追溯；
2. 零 LLM 成本、零失败面、dry-run 预览与实际产物逐字一致（LLM 产物不可预览复现，违背建议器「所见即所执行」哲学）；
3. 可撤销：归档语义 + `notes-archive-undo` 现成；
4. LLM 摘要作为 **Phase 3+ 可选增强**（月志顶部追加一段 LLM 导读），不阻塞 v0。

聚合产物结构（机械拼接 + 机械概览索引——概览即「摘要」的结构化形态）：

```markdown
## 概览

- 2026-08-03 · 会话 a1b2c3d4 ·（首行要点，取原「做了什么」第一条）
- 2026-08-04 · 会话 99f2b674 · …

## 2026-08-03 · 会话 a1b2c3d4

（原日志正文逐字拼接）

## 2026-08-04 · 会话 99f2b674

…
```

**条数增长模型（对数化，量化验收口径）**：

| 口径 | 无卫生（线性） | 有卫生（稳态活跃条数） |
| --- | --- | --- |
| 高强度：30 会话/天 × 1 年 | 原始 ~5000–11000 条/年（会话×日归并后） | 近 7 天日粒度 ≤ 7×30=**210** + 近 90 天周志 ≤ 12 周×W + 月志 12×W（W=工作区数，W=5 时 ≈ **330 条**） |
| 年增长阶 | O(365×会话数/天) | O(12×W)——**对数化达成**（裁决 B② 的「收敛到数百」可验收） |

日志**永不进入** `staleCandidates`/`orphanCandidates`——记录类资产只聚合不淘汰，删除权完全留给用户（回收站/彻底删除现有通道）。

### 6.4 规模量化背书（裁决 B④）

| 项 | 量化 | 结论 |
| --- | --- | --- |
| 单条日志体积 | 1–3 KB（模板骨架 ~200B + 典型内容；front-matter ~400B） | — |
| 年存储（高强度 30 会话/天） | ~5000 条 × 均 2KB ≈ **10 MB/年**；上限口径 30×3KB×365 ≈ 33 MB/年；中位估计 **≈20 MB/年** | 与 `.history` 50 MB 预算同量级且更低，纯文本 Markdown 无需压缩/外置，**存储无压力** |
| 聚合对体积的影响 | 机械拼接只压条数不压字节（字节守恒，另加概览索引 ~5%） | 年存储仍 <50 MB 量级 |
| 内存 | 缓存常驻 ~2KB/条 → 5000 条 ≈ 10 MB、万条 ≈ 20 MB | 可接受；远期可演进 slim 缓存 + 正文按需（RPC 边界已是 slim，演进位现成） |

## 7. ⑤ 检索预留（含裁决 B③：检索分层）

### 7.1 检索分层（定位：L3 是质量升级，不是必需品）

| 层 | 机制 | 承载力 | v0 状态 |
| --- | --- | --- | --- |
| **L1 关键词检索** | 现状：内存缓存常驻 + 线性扫描（`_search` 同路径被 check.js 内存 mock 覆盖） | 万条内扫描 ms 级，**无压力，架构现状即可承载** | 已具备；v0 仅加「默认排除日志 + kind=log 显式召回」口径 |
| **L2 结构化过滤** | front-matter 字段过滤：kind / logDate / topic / tags / folder / sensitive / inject | 随 L1 同扫描，零额外成本 | **v0 交付**（logDate/entities 字段，§7.2） |
| **L3 语义检索** | embedding/向量引擎，走 §7.2 预留字段与插拔位 | 独立索引，不阻塞主库 | **插拔位预留，不实现**——定位质量升级；L1+L2 在万条量级已够用 |

### 7.2 front-matter 字段

| 字段 | v0 | 说明 |
| --- | --- | --- |
| `logDate` | **写入**（YYYY-MM-DD，本地时区；周/月志为周期首日） | 归键与两级聚合的结构化依据（不依赖从 title/createdAt 反推，避免标题被用户改后失键） |
| `entities` | **结构预留，不写值** | 未来语义检索的实体清单（人/项目/服务名）。parseFM 拆分列表加入 `entities`（与 tags 同路径），buildFM 仅非空时落盘（injectRole 同款条件行），noteFromParsed 缺省 `[]`——三处各一行，往返无损即完成「预留」 |
| `topic`/`tags` | 沿用现有 | 语义检索的直接索引面 |
| `sessionId`/`cwd` | 沿用现有 | 跨会话接力与按工作区聚合的依据 |
| `summarizedAt` | 仅 host 自动总结产物写入（ISO 时间） | §5.3 去重节流阀；条件行落盘 |

> parseFM 对未知键本就透传进 meta，但 buildFM 只写已知字段——不补写序列化，任何「预留字段」会在首次 update 时被静默抹掉。**预留 = 往返支持，不是文档声明**，这是 v0 必须带上的几行改动。

### 7.3 检索面适配

- `note_search`/`note_manage list` 的 kind 枚举 + `log`；描述同步「默认结果不含日志，传 kind=log 召回」；
- 正文 `[[双链]]` 现有索引自动覆盖日志的「相关笔记」节——反向链接面板即「哪些日志引用了这条笔记」；
- 未来语义检索落地时，直接以 `kind=log` + `logDate`/`entities`/`topic`/`tags` 为索引维度，无需数据迁移。

## 8. ⑥ 隐私边界

1. **内容敏感性**：会话总结可能含凭据/路径/内部信息。三道闸：(a) 引导模板要求 agent 命中 `sensitiveSuggested` 必落 `sensitive: true`；(b) host 自动总结产物自动过 `suggestSensitive` 命中即敏感（速记口径）；(c) 面板 🔒 随时手动补标。
2. **注入面**：日志 inject 硬 false、recall 默认 false（§6.1），默认零注入面；即便显式 recall=true 进目录，sensitive=true 的标题按行打码 🔒（现有管线自动继承）；目录日志提示行只出计数不出标题。
3. **用户主权**：日志是普通笔记——筛选中心 kind=日志 专入口可见、可编辑、可删（软删除入回收站可恢复、可彻底删除）；引导约定本身同样可编辑/停用/删除。
4. **本地性**：Markdown 落 `~/.dsh/notes`，永不出本机（插件既有属性）；host 自动总结的 LLM 调用会把**会话片段**发往所选模型服务商——这是唯一的出机路径，因此：(a) 默认关；(b) 设置项文案明示「开启后将把会话内容摘要发送给当前模型」；(c) 沿用 settings.llm 的 provider/model 选择权，用户可选本地/内部模型。

## 11. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 与反馈约定双记/指令打架 | 裁决 A 方案本身：单一注入源（约定笔记）+ 模板分工边界段 + 启用时重叠检查与确认（§5.1–5.2） |
| 沉淀开启后数据过多、召回/存储压力 | 裁决 B 机制化：默认隐身（§6.1，日常体验零改变）+ 两级聚合对数增长（§6.3，高强度使用稳态数百条）+ 检索分层（§7.1，万条内 L1 无压力）+ 存储量化背书（§6.4，≈20MB/年 << 50MB 参照） |
| 日志泛滥挤占目录索引 | recall 默认 false 根本不进目录；一条计数提示行恒占用一行以内 |
| agent 不按约定写（引导失效） | 约定用户可见可改（可收紧文案）；host 自动总结兜底（Phase 3）；接受覆盖率渐进——约定引导是零成本通道 |
| idle 误判导致乱写 | v0 默认不把 idle 当写入触发；Phase 3 也有去抖 + 去重 + 只追加不覆盖三重闸（§5.3） |
| 敏感信息进日志 | §8 三道闸 + 出机路径默认关且明示 |
| 多通道写同一条日志竞态 | 归键一致 + `_create`/`_update` 单存储路径；quickChain 同款串行化可复用 |

## 12. 评审检查单与开放问题

**评审检查单**：
1. 写入通道是否严格符合裁决 A（无独立注入管线、边界声明、重叠检查）；
2. 默认隐身口径是否严格符合裁决 B①（inject 硬 false / recall 默认 false / 列表与默认搜索排除、筛选中心为专入口），「显式 recall=true 允许进目录」的豁免是否认可；
3. 两级聚合窗口（7 天 / 90 天）与机械拼接决策是否认可（裁决 B②）；
4. 规模量化（§6.3 条数模型、§6.4 存储）是否足以背书「无压力」结论；
5. logDate/entities/summarizedAt 的「往返式预留」是否过度设计；
6. 分期切分是否符合发布节奏。

**开放问题**：
1. Phase 3 的 live 会话消息读取 API 需在开发期核验（`agents.get()` 消息面；冷读已排除）——若 API 不存在，Phase 3 降级为「仅提醒用户该会话未沉淀」；
2. 引导笔记发现键用 tag `memory-guide`（零 schema 变更）还是专用 front-matter 标记——设计推荐 tag，评审可推翻；
3. 面板「沉淀本会话」快捷按钮（向当前会话注入一句沉淀指令）是否进 Phase 1——设计列为可选项，不进核心；
4. 月聚合归组维度含「工作区」——跨工作区同月是否合为一篇全局月志，评审可选（设计默认按工作区分组，保持归属清晰）。
